3What's Missing Today — The Problem

The current system has 11 agents that work in complete isolation. No agent knows what another has done with the same lead. Here are the active information silos:

Aria calls leads who already replied via WANo agent checks if a lead replied to WhatsApp before placing a voice call. Aria is blind to WA history.
Email sends ignore active WA conversationsThe 6-step email sequence fires even when a prospect is mid-conversation via WhatsApp.
Silent failures — zero alertsEvery cron job has except: pass. If the WA token expires, agents send 0 messages and no one is notified.
No system memoryThere is no persistent record of architecture decisions, upgrade history, or what was tried and failed.
No learning loopThe system has been running for months. No agent has extracted a single pattern from the data — which messages work, which cities convert, which scripts close.
No command channelTo pause outreach to dentists in Toronto, you'd need to edit code and redeploy. There is no runtime directive system.

4CEO Agent — What It Does

A. System Heartbeat every hour

Reads agent_registry, recent lead_activities, active Vapi calls, and email queue depth. Writes a health snapshot to system_journal. Sends a WA alert only when something is broken — not noise, only signal.

B. Lead Context Enrichment fixes information silos

A new shared function get_lead_context(lead_id) that every agent calls before acting. Instead of agents running blind, every agent gets a full picture:

Lead: Bright Smiles Dental, Melbourne
Contact history:
  - WA outreach sent 5 days ago (no reply)
  - Email 1 sent 3 days ago (opened, not clicked)
  - Email 2 sent today
  - WA follow-up sent yesterday

Touchpoints: 4  |  Engagement: LOW
Last contact: 18h ago
Recommended next action: Voice call appropriate

This context is injected into Aria's system prompt, the personalizer template, and every follow-up generator. Every agent becomes dramatically smarter.

C. Directive Queue runtime control

New agent_directives table. CEO writes directives; each agent checks the queue before running:

DirectiveEffectExample
PAUSEStop all sends to a business type or cityPause dentist outreach in Toronto
ADJUST_INTERVALChange follow-up timing on the flyReduce WA follow-up to 2 days for AU leads
CHANGE_TEMPLATESwitch to a different WA/email templateUse template B for physiotherapists this week
TARGETFocus pipeline on a specific city + typeRun dentist prospecting in Sydney only
ABORT_LEADImmediately stop all contact with a leadRemove Dr. Smith — called to complain

5Brain Agent — What It Does

A. Daily Data Accumulation 2am UTC

Reads new lead_activities since last run. Extracts raw signals: reply rates by message template, email engagement by subject line and business type, call outcomes by script, time-of-day response patterns.

B. Weekly Deep Learning Sunday midnight

Full analysis of the past 7 days using Claude Opus:

  • What's working: Top 3 messages, business types, cities, time windows
  • What's failing: Low-reply templates, dropout points in the funnel
  • Client voice: Themes extracted from WA replies and call transcripts — what objections come up, what language resonates
  • Funnel analysis: Where are prospects falling off? Outreach → Email → Call → Reply → Demo

Results are stored in learnings and knowledge_base tables.

C. Advice Engine queryable anytime

You or the CEO can query the Brain at any time via /api/brain/query:

QueryExample Answer
Which business type to focus on?Physiotherapists: 34% reply rate vs 18% average. Push Melbourne + Sydney.
Should we reduce WA follow-up to 2 days?Based on 847 leads, 40% of replies arrive after day 3. Do not reduce interval.
What objections do prospects raise?Price (38%) · Existing system (24%) · Too busy (19%) · Not interested (11%)
Best time to call dentists in Melbourne?Tuesday–Thursday, 10–11 AM AEST. 2.4× higher answer rate.

D. Architecture Audit monthly + on-demand

Beyond learning from data, Brain periodically audits the agent architecture itself — asking whether the right agents exist, whether they are doing the right things, whether any are redundant or missing, and whether the system is cost-efficient. This is the self-improvement loop that prevents architectural drift.

For each agent in agent_registry, Brain evaluates:

  • Contribution: Does this agent's output demonstrably move leads toward conversion?
  • Overlap: Is another agent doing the same job, creating duplicate sends or wasted API calls?
  • Gap coverage: Is there a channel, timing window, or lead state that no agent handles?
  • Cost efficiency: Is this agent using the right model (Haiku vs Sonnet vs Opus) for its task? Is it running too frequently?
  • Complexity vs value: Is this agent complex to maintain but producing marginal results?

Each audit produces a structured report with one verdict per agent:

Architecture Audit Report — June 2026
Generated by: Brain Agent | Based on: 847 leads, 3 months of activity

KEEP    Agent 3  Personalizer      High impact — 23% reply rate vs 9% generic WA
KEEP    Agent 7  Voice Follow-up   2.1× conversion vs WA-only leads in AU
MODIFY  Agent 6  WA Follow-up      Reduce interval 3→2 days; 68% of day-3 sends are to already-dead leads
MODIFY  Agent 10 Observatory       Add 2h watchdog; current silent-failure rate is unacceptable
MERGE   Agent 4+5 Reply+Booking   Already co-located in reply_handler.py; formalise as one "Engagement" agent
ADD     SMS Agent                 AU regulations permit; 34% of AU leads have no email on record
REVIEW  Agent 8  Content           Planned but unbuilt; defer — pipeline not yet stable enough to warrant
COST    Agent 2  Email Scraper     Using Sonnet for HTML parsing — Haiku sufficient; est. $12/mo saving

The audit report is stored in the new architecture_reviews table with status proposed. It is then passed to the CEO, who packages it as a clear WA brief to Neeraj. Nothing changes until Neeraj approves.

E. Architecture Evolution

Once Brain has accumulated sufficient cross-vertical data, it can go further — drafting a complete new multi-agent system spec for a new vertical or product (e.g., real estate, restaurants, LegalAidAI cross-sell) as a structured JSON document the CEO and Neeraj can review before any code is written.

7New Supabase Tables

CREATE TABLE agent_registry (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name            TEXT UNIQUE NOT NULL,     -- 'wa_followup', 'voice_outreach', etc.
  description     TEXT,
  status          TEXT DEFAULT 'active',    -- active | paused | error
  last_run_at     TIMESTAMPTZ,
  last_run_result JSONB,                   -- {processed, sent, failed, error}
  config          JSONB DEFAULT '{}',        -- adjustable params per agent
  created_at      TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE agent_directives (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  agent       TEXT NOT NULL,
  directive   TEXT NOT NULL,              -- PAUSE | ADJUST | TARGET | ABORT_LEAD
  params      JSONB DEFAULT '{}',
  status      TEXT DEFAULT 'pending',     -- pending | applied | expired
  issued_by   TEXT DEFAULT 'ceo',
  created_at  TIMESTAMPTZ DEFAULT now(),
  applied_at  TIMESTAMPTZ
);

CREATE TABLE system_journal (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  entry_type  TEXT NOT NULL,              -- health_check | alert | decision | directive_issued
  summary     TEXT,
  detail      JSONB DEFAULT '{}',
  created_at  TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE learnings (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  category     TEXT NOT NULL,             -- message_effectiveness | timing | client_voice
  insight      TEXT NOT NULL,
  confidence   FLOAT DEFAULT 0.5,          -- 0–1, based on sample size
  data_points  INT DEFAULT 0,
  period_start TIMESTAMPTZ,
  period_end   TIMESTAMPTZ,
  created_at   TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE knowledge_base (
  id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  topic      TEXT UNIQUE NOT NULL,        -- 'top_performing_messages', 'objection_map'
  content    TEXT,                          -- markdown or structured JSON summary
  updated_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE architecture_reviews (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  triggered_by    TEXT DEFAULT 'scheduled',   -- scheduled | neeraj_request | ceo_request
  summary         TEXT,                          -- plain-English brief sent to Neeraj via WA
  recommendations JSONB,                         -- [{agent, verdict, rationale, cost_impact}]
  status          TEXT DEFAULT 'proposed',      -- proposed | awaiting_neeraj | approved | rejected | partial
  neeraj_response TEXT,                          -- verbatim WA reply from Neeraj
  approved_items  JSONB,                         -- subset of recommendations Neeraj approved
  implemented_at  TIMESTAMPTZ,
  created_at      TIMESTAMPTZ DEFAULT now()
);

9Governance & Approval Chain

Every structural recommendation — adding, removing, merging, or modifying an agent — flows through a mandatory approval chain. The system proposes. Neeraj decides. Nothing is self-authorised.

B
Brain Agent — Generates Audit Report
Analyses all agents against data. Produces verdicts: ADD / REMOVE / MERGE / MODIFY / KEEP / COST. Stores in architecture_reviews with status proposed.
C
CEO Agent — Packages & Delivers Brief
Reads the audit report. Compresses into a clear, plain-English WhatsApp message. Sends to Neeraj's number. Updates review status to awaiting_neeraj. Does not act on any recommendation yet.
N
Neeraj — Reviews & Decides (via WhatsApp)
Replies in plain English. Can approve all, approve some, reject all, ask follow-up questions, or request a deeper analysis. Example responses:
"Approve all" CEO implements every recommended change
"Approve 1 and 3, skip 2" CEO implements items 1 & 3 only, logs 2 as rejected
"Not now, revisit in 30 days" Review deferred, Brain re-evaluates next cycle
"Reject all" All recommendations logged as rejected, no action taken
C
CEO Agent — Executes Approved Changes Only
Implements exactly what Neeraj approved — no more. Logs each action to system_journal. Updates architecture_reviews.implemented_at. Sends Neeraj a confirmation: "Done — Agent 6 follow-up interval updated to 2 days. Agent 4+5 merged. Everything else unchanged."
Master Mandate
  • No agent is added, removed, merged, or structurally modified without Neeraj's explicit approval via WhatsApp
  • The Brain and CEO can propose, analyse, cost-model, and draft code — but none of it deploys until Neeraj signs off
  • Neeraj can approve partially: "do 1 and 3 but not 2" is a valid and fully supported response
  • All decisions — approvals AND rejections — are logged to system_journal and architecture_reviews permanently
  • Operational changes (pause a campaign, change a template, adjust timing) still go through the CEO but do not require an architecture review — Neeraj can approve those in real time via a simple WA reply
